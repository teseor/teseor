# v0.3 spec-format design

Status: proposed — 2026-05-22

## Why

v0.2 shipped one component (Button) end-to-end and proved the codegen loop. v0.3
authors the first wave of Phase 1 components — 13 atoms plus the first two
headless overlays (Tooltip, Popover) and the `@teseor/primitives` package. The
spec format has to be settled before those specs are written, so the 60-plus
component specs still ahead are authored once against a stable, enforced shape.

Reviewing the current state surfaced a gap that reframes the work: **the spec
validator described in `architecture/codegen-pipeline.md` does not exist.**
`lint:spec` is a no-op stub (`echo … && exit 0`), `scripts/codegen/src/`
contains no validation logic, and the doc's "Spec validation" section and its
"schema is frozen / rejects unknown fields" claim describe software that was
never built. `button.yaml` already carries `constraints:`, `motion:`, and
`responsive:` flags that nothing checks. The spec-to-CSS token contract is
unverified in either direction.

So the v0.3 spec-format work has a keystone: a real validator has to exist
before "activate a field" or "enforce a decision" mean anything.

## Decisions

### 1. Validator keystone

Build a real `validate-spec.ts`, wired into `pnpm lint` (replacing the
`lint:spec` stub) and pre-commit. It works in two layers:

- **Shape** — the spec parses against the schema in decision 2; unknown fields
  are rejected.
- **Semantics** — cross-checks no schema library can express:
  - every `tokens:` entry is declared as `--t-<name>-*` in the component CSS,
    and every `--t-<name>-*` in the CSS is listed in `tokens:` — closes the
    spec-to-CSS hole;
  - `examples:` reference real variant / intent / size values;
  - `constraints:` hold against every `examples:` entry and every expanded
    `matrix:` cell;
  - the vocabulary check (canonical names, Levenshtein suggestions) from
    `rules/naming.md`.

The same effort corrects `architecture/codegen-pipeline.md` so it describes the
validator as built, not as imagined.

### 2. Schema model

A spec is an **identity layer** plus a **`ComponentNode`**.

- **Identity layer** — root only, never recurses: `name`, `kind`,
  `description`, `dependencies`, `file`, `behavior`, `primitives`, `guidance`,
  `examples`, `matrix`. These describe the component as a published unit.
- **`ComponentNode`** — recursive: `element`, `rootClass`, `variants`,
  `intents`, `sizes`, `props`, `tokens`, `private`, `states`, `a11y`,
  `constraints`, and an optional `parts:` map of further `ComponentNode`s.

`kind:` is a discriminated union over an **open** set:

- `atomic` — the `ComponentNode` is inlined flat at the root (today's
  `button.yaml` shape, unchanged).
- `composite` — the root carries a `parts:` map; each part is a
  `ComponentNode`, nesting freely.

The set is left open so a later **form-composition** kind (a `Field` wiring
`for` / `aria-describedby` across independent components) can be added without a
breaking schema change.

Atomic specs stay flat — no `parts:` key, no nesting under a `root` part. The
same `ComponentNode` schema validates both forms; the uniformity is internal,
the flat authoring is preserved for the simple components.

Within-part constraints live on the node; a constraint spanning two parts lives
at the identity layer, since no single node owns it.

### 3. Fields activated for v0.3

- **`parts:`** — recursive per decision 2. The schema is designed to the depth
  `Table` (v0.5) will need; codegen is built only to the depth Tooltip and
  Popover need. A deeper component later extends codegen, never the schema.
- **`behavior:` + `primitives:`** — `behavior: none | primitive | stateful`;
  `primitives:` lists the required behavior utilities. Forced — Tooltip and
  Popover are headless.
- **`pattern: controllable`** — expands a value-bearing prop into the
  controlled / uncontrolled / change-callback triple. Forced — Checkbox, Radio,
  Switch, Select.
- **`guidance:`** — docs-page prose (when to use, when not, variant choice,
  content rules, common mistakes). Its YAML shape was never drafted; drafting it
  is a sub-task of this work.
- **`a11y:` state mapping** — extend the existing `a11y:` block with a
  state-to-attribute map (`loading` to `aria-busy`, `checked` to
  `aria-checked`, …), so codegen emits ARIA deterministically and contract tests
  assert it. This has to be the single ARIA mechanism — coordinated with
  `interactions:` (#582), not parallel to it.
- **`states:`** — promoted from a bare list to a map with a `description:` per
  state, consistent with `variants` / `intents` / `sizes`.

### 4. Deferred

- **`stability:`** — `alpha` / `beta` / `stable` / `deprecated`. Pure metadata,
  no structural capability, addable in any later milestone; pre-1.0 the signal
  is weak and promotion discipline is uncommitted. Revisit when the component
  set has a real maturity spread.

### 5. The five v0.3 issues

| Issue | Decision |
| --- | --- |
| #594 — per-prop responsive enforced | Keep, re-scoped. Not a format change but an enforcement one: the validator rejects a non-slot prop that omits `responsive:`. Rule into `docs/rules/responsive.md`; the `new-component` scaffold prompts the decision. Gated on the keystone. |
| #597 — constrain `as` | Keep. Reuses the `values:` mechanism — `as: { type: string, values: [button, a] }`. Open sub-question recorded on the issue: whether custom (non-element) React components stay allowed. |
| #581 — `matrix:` expansion | Keep. Needs an ADR: cartesian vs pairwise. |
| #582 — `interactions:` block | Keep. Coordinate with the decision-3 `a11y:` mapping so behavior and ARIA assertions share one mechanism. |
| #593 — export enum types | Exits this effort. It changes only generator output and barrel re-exports; `specs/<name>.yaml` does not change. Stays a v0.3 milestone issue, no ADR. |

### 6. Recorded, not solved

- **Form-context composition** — `Field` / `Fieldset` / `Form` wire
  accessibility relationships across independent components; neither `parts:` (a
  state-sharing family) nor `dependencies:` (a bare import) covers it. The open
  `kind:` discriminator leaves room; the mechanism is a v0.4 forms decision.
- **Component families** — `Number Input`, `Password Input`, `Search Input` are
  structural variations of `Input`, not visual variants. There is no `extends:`
  mechanism. The v0.3 `Input` spec should be authored aware that a family is
  coming.
- **Iteration stays consumer-side** — `Menu`, `Table`, `Breadcrumb`,
  `Pagination` render N items, but the consumer maps data to part instances (the
  Radix model). The spec format gets no `data:` binding concept — a deliberate
  non-decision.

### 7. Roadmap correction

`parts:` moves from v0.4 to v0.3: Popover is structurally multi-part and the
roadmap commits to the Radix headless-utility model.

## Open questions for the ADRs

- Schema library — Zod, valibot, or hand-rolled. The shape layer benefits from
  an inferred type shared with the generators; the semantic layer is custom code
  regardless. The schema POC informs this.
- `matrix:` — cartesian (every combination) vs pairwise (covering set). #581.
- `as` — whether custom React components stay allowed under the constrained
  type. #597.
- `guidance:` — the YAML shape.
- Whether the schema decision is a new ADR or an amendment to ADR-0002 (the
  per-component spec). Recommended: a new ADR extending ADR-0002 — amending an
  existing ADR needs maintainer sign-off, and a new ADR keeps cleaner
  provenance.

## Deliverables and sequence

1. This design doc.
2. **Schema POC** — author a `popover.yaml` against the decision-2 schema and a
   minimal `validate-spec.ts` that parses it. Pressure-tests the recursive
   `ComponentNode` shape and informs the schema-library choice, before the ADR
   freezes anything. Its output is not throwaway — it is the first slice of the
   keystone.
3. **ADR — spec schema and validation** — decisions 1 and 2.
4. **ADR — `matrix:` expansion** — cartesian vs pairwise.
5. **Issues** — one new issue for the validator keystone; new or updated issues
   for the field activations; re-scope #594 / #597 / #581 / #582 in place.

Component implementation (the 13 atoms, Tooltip, Popover) begins only after the
ADRs are settled.
