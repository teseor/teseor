# 0001 — The v0.3 spec format

## Summary

Settle the `specs/<name>.yaml` format ahead of the v0.3 component wave: build
the spec validator (`validate-spec.ts`) that the docs describe but the
codebase never has; restructure the schema as an identity layer plus a
recursive `ComponentNode`, gated by an open `kind:` discriminated union
(`atomic` first, `composite` for `parts:`-based families, a third kind
reserved for v0.4 form composition); activate the reserved fields v0.3
components force (`parts:`, `behavior:` / `primitives:`, `pattern: controllable`);
add a state-to-attribute mapping to `a11y:`; promote `states:` from a list to a
map; defer `stability:`; re-scope the five existing v0.3 spec-format issues;
drop #593 from the spec-format effort because it changes only generator output.

## Motivation

v0.2 shipped one component (Button) end-to-end and proved the codegen loop.
v0.3 authors 13 atoms plus the first two headless overlays (Tooltip, Popover)
and the `@teseor/primitives` package. The format has to be stable and enforced
before those specs are written, so the 60-plus component specs still ahead are
authored once against a shape the validator catches mistakes against.

Reviewing the current state surfaced a gap that reframes the work: **the spec
validator described in `architecture/codegen-pipeline.md` does not exist.**
`lint:spec` is a no-op stub (`echo … && exit 0`), `scripts/codegen/src/`
contains no validation logic, and the doc's "Spec validation" section and its
"frozen schema that rejects unknown fields" claim describe software that was
never built. `button.yaml` already carries `constraints:`, `motion:`, and
`responsive:` flags that nothing checks; the spec-to-CSS token contract is
unverified in either direction.

So the v0.3 spec-format work has a keystone: a real validator has to exist
before "activate a field" or "enforce a decision" mean anything.

## Detailed design

### 1. Validator keystone

Build a real `validate-spec.ts`, wired into `pnpm lint` (replacing the
`lint:spec` stub) and pre-commit. Two layers:

- **Shape** — a spec parses against the schema in §2; unknown fields are
  rejected.
- **Semantics** — cross-checks no schema library can express:
  - every `tokens:` entry is declared as `--t-<name>-*` in the component CSS,
    and every `--t-<name>-*` declared in the CSS is listed in `tokens:` —
    closes the spec-to-CSS hole;
  - `examples:` reference real variant / intent / size values;
  - `constraints:` hold against every `examples:` entry and every expanded
    `matrix:` cell;
  - the vocabulary check (canonical names, Levenshtein suggestions) from
    `rules/naming.md`.

The same effort corrects `architecture/codegen-pipeline.md` so it describes
the validator as built, not as imagined.

### 2. Schema model

A spec is an **identity layer** plus a **`ComponentNode`**.

- **Identity layer** — root only, never recurses: `name`, `kind`,
  `description`, `dependencies`, `file`, `behavior`, `primitives`, `guidance`,
  `examples`, `matrix`. These describe the component as a published unit.
- **`ComponentNode`** — recursive: `element`, `rootClass`, `variants`,
  `intents`, `sizes`, `props`, `tokens`, `private`, `states`, `a11y`,
  `constraints`, `motion`, and an optional `parts:` map of further
  `ComponentNode`s.

`kind:` is a discriminated union over an **open** set:

- `atomic` — the `ComponentNode` is inlined flat at the root (today's
  `button.yaml` shape, unchanged).
- `composite` — the root carries a `parts:` map; each part is a
  `ComponentNode`, nesting freely.

The set is left open so a later **form-composition** kind (a `Field` wiring
`for` / `aria-describedby` across independent components) can be added
without a breaking schema change.

Atomic specs stay flat — no `parts:` key, no nesting under a `root` part. The
same `ComponentNode` schema validates both forms; the uniformity is internal,
the flat authoring is preserved for the simple components.

Within-part constraints live on the node; a constraint spanning two parts
lives at the identity layer, since no single node owns it.

`element` and `rootClass` are optional on a `ComponentNode`: a part can be
behavioral-only — Popover's `root` part is a state provider that renders no
DOM (the Radix model). The validator's semantic layer requires them on
atomic specs and on any rendering part, and allows their absence on a
provider part.

### 3. Fields activated for v0.3

- **`parts:`** — recursive per §2. The schema is designed to the depth
  `Table` (v0.5) will need; codegen is built only to the depth Tooltip and
  Popover need. A deeper component later extends codegen, never the schema.
- **`behavior:` + `primitives:`** — `behavior: none | primitive | stateful`;
  `primitives:` lists the required behavior utilities. Forced — Tooltip and
  Popover are headless.
- **`pattern: controllable`** — expands a value-bearing prop into the
  controlled / uncontrolled / change-callback triple. Forced — Checkbox,
  Radio, Switch, Select.
- **`guidance:`** — docs-page prose (when to use, when not, variant choice,
  content rules, common mistakes). Its YAML shape was never drafted; drafting
  it is a sub-task of this work.
- **`a11y:` state mapping** — extend the existing `a11y:` block with a
  state-to-attribute map (`loading` to `aria-busy`, `checked` to
  `aria-checked`, …), so codegen emits ARIA deterministically and contract
  tests assert it. This has to be the single ARIA mechanism — coordinated
  with `interactions:` (#582), not parallel to it.
- **`states:`** — promoted from a bare list to a map with a `description:`
  per state, consistent with `variants` / `intents` / `sizes`.

### 4. Deferred

- **`stability:`** — `alpha` / `beta` / `stable` / `deprecated`. Pure
  metadata, no structural capability, addable in any later milestone;
  pre-1.0 the signal is weak and promotion discipline is uncommitted.
  Revisit when the component set has a real maturity spread.

### 5. The five v0.3 issues

| Issue | Decision |
| --- | --- |
| #594 — per-prop responsive enforced | Keep, re-scoped. Not a format change but an enforcement one: the validator rejects a non-slot prop that omits `responsive:`. Rule into `docs/rules/responsive.md`; the `new-component` scaffold prompts the decision. Gated on the keystone. |
| #597 — constrain `as` | Keep. Reuses the `values:` mechanism — `as: { type: string, values: [button, a] }`. Open sub-question recorded on the issue: whether custom (non-element) React components stay allowed. |
| #581 — `matrix:` expansion | Keep. Needs an ADR: cartesian vs pairwise. |
| #582 — `interactions:` block | Keep. Coordinate with §3's `a11y:` mapping so behavior and ARIA assertions share one mechanism. |
| #593 — export enum types | Exits this effort. It changes only generator output and barrel re-exports; `specs/<name>.yaml` does not change. Stays a v0.3 milestone issue, no ADR. |

### 6. Roadmap correction

`parts:` moves from v0.4 to v0.3: Popover is structurally multi-part and the
roadmap commits to the Radix headless-utility model.

### 7. POC outcome (2026-05-23)

A runnable POC — the schema as Zod, a `popover.yaml` fixture, and the three
existing specs — validated §2:

- The recursive `ComponentNode`, the identity/node split, and the open
  `kind:` discriminated union express cleanly in Zod (`z.lazy()` for the
  recursion, strict objects for unknown-field rejection). Zod for the shape
  layer is viable.
- `stack.yaml` and `cluster.yaml` validate against the new schema unchanged.
  `button.yaml` fails on exactly one field — `states:` is a list, not a map
  — which is the §3 migration. The whole migration cost is converting
  `states:` to a map wherever it appears (today, `button.yaml` only).
- The `popover.yaml` composite — DOM-less `root` part, per-part `variants`
  / `sizes` / `tokens` / `a11y` / `motion`, `pattern: controllable`, the
  `a11y.states` attribute map — validates. The composite shape holds.

## Drawbacks

- A new dependency, whichever schema library is picked. Teseor is
  dep-frugal; adds an audit surface.
- `button.yaml` requires a one-field migration (`states:` list to map).
  Tiny, but a change to the (repo-internal) spec format.
- The validator itself is non-trivial code to maintain: schema declarations
  plus a custom semantic-check pass (cross-file token checks, vocabulary
  Levenshtein).
- Pulling `parts:` into v0.3 commits the recursive shape before Table
  (v0.5) exists. The schema is closed under composition by construction (a
  part is a `ComponentNode`), but the codegen path is unverified at depth
  until Table lands.
- `guidance:` activates with an undesigned YAML shape. Designing it is an
  in-flight sub-task; the proposal expands during implementation.

## Alternatives

- **Defer the validator** — keep `lint:spec` a stub for one more milestone,
  decide field shapes only. Rejected: 13 components ship against an
  unenforced format, compounding the existing drift; the validator gets
  costlier to retrofit once specs proliferate.
- **Minimal validator (shape only, no semantic checks).** Rejected: the
  spec-to-CSS token-contract hole is the deepest drift risk in the
  codebase, and only a custom semantic pass catches it. Without it the
  validator buys unknown-field rejection only — useful but not load-bearing.
- **Closed `kind:` union** (`atomic | composite`). Rejected: the full
  component list (`Field` / `Fieldset` / `Form` / `Form Error` / `Form
  Helper` / `Label`) shows a third kind is needed for form-context
  composition; a closed union forces a breaking schema change later.
- **Bespoke shallow `parts:`** for Tooltip / Popover only. Rejected: a
  re-cut when Table lands migrates Accordion, Tabs, Menu, Popover, and
  Tooltip specs. The recursive shape (`part = ComponentNode`) is closed
  under composition by structural identity, not a forecast of Table's
  features — there is nothing to redesign.
- **Hand-roll the schema validation.** Possible — semantic checks are
  hand-rolled regardless. But the shape layer benefits from an inferred
  type shared with the generators (today each generator hand-maintains its
  own `Spec` types). A schema library carries its own weight in that
  consolidation. The library choice (Zod vs valibot vs hand-rolled) is
  settled in the schema-and-validation ADR; this RFC scopes the *shape*,
  not the runtime.

## Adoption strategy

Internal change. No public consumer surface is affected — `@teseor/css`
publishes CSS, and the wrappers (`@teseor/react` / `@teseor/vue`) are
regenerated from the new schema, so the consumer-visible result is
unchanged modulo intentional improvements (correct ARIA mapping, the
constrained `as` type from #597, controlled/uncontrolled triples on future
Checkbox).

Migration inside the repo:

- `button.yaml` — `states:` list to map. One file, one field.
- `stack.yaml`, `cluster.yaml` — no change.
- `architecture/codegen-pipeline.md` — corrected to describe the validator
  as built, in the same PR.

No codemod is needed; the migration is one hand-edit to one file.

## Unresolved questions

- The schema library — Zod (POC-confirmed viable), valibot, or hand-rolled.
  Settled in the schema-and-validation ADR.
- `matrix:` — cartesian vs pairwise. Settled in the `matrix:` ADR (#581).
- `as` — whether custom React components stay allowed under the constrained
  type. Settled on #597.
- `guidance:` — the YAML shape.
- Whether `motion:` is required. `codegen-pipeline.md` says yes;
  `stack.yaml` and `cluster.yaml` ship without it. The validator either
  enforces it (those two migrate) or it stays optional for components with
  no transitions.
- The `examples:` shape for composite specs — example props address parts
  (`props: { content: { size: md } }`), so the examples schema is
  kind-dependent and the validator's combination check needs the per-part
  mapping.
- Whether the schema decision is a new ADR or an amendment to ADR-0002.
  Recommended: a new ADR extending ADR-0002 — amending an existing ADR
  needs maintainer sign-off, and a new ADR keeps cleaner provenance.

## What this doesn't propose

- **Form-context composition.** `Field` / `Fieldset` / `Form` wire
  accessibility relationships across independent components; neither
  `parts:` (a state-sharing family) nor `dependencies:` (a bare import)
  covers it. The open `kind:` discriminator leaves room; the mechanism is a
  v0.4 forms decision.
- **Component families / spec inheritance.** `Number Input`, `Password
  Input`, `Search Input` are structural variations of `Input`, not visual
  variants. There is no `extends:` mechanism. The v0.3 `Input` spec should
  be authored aware that a family is coming, but the mechanism waits.
- **Iteration as a spec concept.** `Menu`, `Table`, `Breadcrumb`,
  `Pagination` render N items, but the consumer maps data to part
  instances (the Radix model). The spec format gets no `data:` binding
  concept — a deliberate non-decision.
- **Component implementation.** No CSS, behavior files, wrappers, or tests
  for the v0.3 components land in this RFC. Implementation begins after
  the ADRs that flow from it.
- **#593 (enum-type exports).** Generator-output change only; no
  spec-format impact.
