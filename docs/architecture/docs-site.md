# Docs site

The docs site is itself a Teseor showcase. Its layout, nav, and per-component pages are built with `.t-*` classes — no themed doc framework, no parallel styling system. Dogfood rule (H3).

## Stack

- **Astro** — static-site builder with no built-in theme, so Teseor owns every visual. Renders `@teseor/*` component packages to static HTML at build time (zero client JS unless a `client:*` directive opts in) — the docs consume the real generated wrappers. See ADR-0007.
- **Shiki** — build-time syntax highlighting. Zero runtime cost.
- **Pagefind** — self-hosted search, indexed at build time from emitted HTML. No SaaS, no client-side bundle weight.
- **Vanilla JS** — tab switching, theme switching, copy-to-clipboard. ~100 lines total. No framework runtime.
- **Deploy:** Cloudflare Pages at `teseor.dev`. Git-push-to-deploy, preview deployments per PR.

We rejected Starlight, Vitepress, and Docusaurus: each ships its own theme that fights the dogfood rule. Plain Astro ships no theme — it is the unopinionated builder we wanted, and unlike Eleventy it renders the DS's own component packages. Hand-rolled was rejected as "false simplicity" — reinventing search and syntax highlighting consumes the budget we save on stack weight.

## Per-component page anatomy

Every component's page follows a fixed section order, generated from `specs/<name>.yaml`:

1. **Live preview** — see "Demo UX" below
2. **When to use / not** — from `spec.guidance.when` / `whenNot`
3. **Choosing a variant** — from `spec.guidance.variantChoice`
4. **Anatomy** — SVG diagram with callouts
5. **Variants / Intents / Sizes** — from `spec.variants` / `intents` / `sizes`
6. **Content guidelines** — from `spec.guidance.contentRules`
7. **Layout & density**
8. **States** — from `spec.states` (default, hover, focus, disabled, loading)
9. **API reference** — framework-tabbed; see "API tabs" below
10. **Tokens** — public token table from `spec.tokens`
11. **Accessibility** — from `spec.a11y`
12. **Common mistakes** — from `spec.guidance.commonMistakes`
13. **Recipes** — links to `docs/recipes/`

Sections are skipped when the corresponding spec field is empty. `gen-docs` reads the spec and emits the data file Astro consumes.

**Quality bar:** a junior designer reading only sections 2, 3, and 6 (When / Variant / Content) makes correct choices 90% of the time. If they get it wrong, the doc has failed — rewrite those three sections, don't add caveats elsewhere.

## Demo UX

Each `spec.examples` entry renders as one demo block. Four richness levels exist; **L2 is the v0.2 ship target**.

| Level | Shows | Scope |
| --- | --- | --- |
| L1 | Rendered component only | trivial |
| **L2** | **Component + framework tabs (React/Vue/Svelte/Angular/WebC/HTML+CSS) + Shiki-highlighted code + Copy button** | **v0.2** |
| L3 | L2 + live controls (variant/intent/size dropdowns that re-render in-place) | v0.3-v0.4 |
| L4 | External StackBlitz/CodeSandbox link | post-v1.0 |

L2 layout per demo block:

```text
┌─────────────────────────────────────┐
│  [ rendered example, static HTML ]   │
├─────────────────────────────────────┤
│  [React][Vue][Svelte][Ang][WC][HTML] │
│  ─────                               │
│  <Button variant="solid" />          │
│                              [Copy]  │
└─────────────────────────────────────┘
```

The framework code per tab is generated by the matching `gen-<target>` from the same spec — one source of truth, six views. The rendered preview is plain HTML emitted at build time using Teseor's classes; no client-side framework runtime.

The demo block UI itself is built from Teseor's own Tabs, Button, and Code components — full dogfood. Tabs lands in v0.3, paged in early for docs.

## API tabs

The "API reference" section uses the same framework tab pattern as demos. Last-selected framework persists via cookie across the site (every component page opens to your preferred framework). Framework-agnostic content (Variants, Tokens, Accessibility tables) lives *above* the tabs and never switches.

## `guidance:` spec field

Designed at v0.2 alongside `constraints:`. Shape:

```yaml
guidance:
  when:
    - "Primary action on a form"
    - "Single most important call-to-action on a view"
  whenNot:
    - "Link navigation — use Anchor"
    - "Toggleable state — use Switch"
  variantChoice:
    solid: "The default visual weight; one per view"
    outline: "Secondary actions positioned next to a solid"
    ghost: "Tertiary actions, dense UI, button groups"
  contentRules:
    - "Label is a verb in the imperative ('Save', not 'Saving')"
    - "Max 3 words"
  commonMistakes:
    - mistake: "Two solid buttons side by side"
      fix: "Demote one to outline"
    - mistake: "Ghost button as a view's only CTA"
      fix: "Promote to solid or outline"
```

Markdown allowed in string values. `gen-docs` reads `guidance:` to fill sections 2, 3, 6, and 12 of the page.

**Keying rule for `variantChoice:`.** `validate-spec.ts` requires `variantChoice` keys to equal `spec.variants` exactly — every declared variant has a one-line choice rationale, and no orphan keys are tolerated. A missing variant or an unknown key fails the lint gate.

## Search

Two complementary search surfaces:

- **Pagefind** (build-time index of rendered HTML) handles prose search across docs pages, recipes, and component pages. Free, no SaaS, post-build indexing of static HTML.
- **Faceted search** at `/search` (ships v0.3) queries `apps/docs/src/_data/teseor-ast.json` (the structured DS representation from `gen-ast.ts`) client-side. Filters by token (name, family, type), component (name, variant, intent, size), recipe. Same JSON powers any downstream tooling (`@teseor/contract/ast.json` republished form) — MCP servers, theme inspectors, third-party docs.

Pagefind covers prose; the AST page covers structured introspection. Build artifacts on one site, no runtime backend.

## SEO: sitemap

`sitemap.xml` generated at build time via `@astrojs/sitemap` from the page set. Linked from `robots.txt` at the site root. Ships with v0.3 deployment. Cheap, standard, helps the docs site rank on its own keywords (`teseor button`, `teseor tokens`, etc.) rather than ceding ground to third-party tutorial sites.

## Auto-generated navigation

The sidebar is generated from filesystem layout — `components/atomic/*`, `components/surface/*`, `components/composite/*` become top-level groups. Per-group ordering comes from `spec.order` (integer, lower first). Group titles from `spec.group` or the directory name. No manual nav file to drift.

## Recipes

Multi-component compositions (Modal+Form, Drawer+Tabs, Toast+Action) live at `docs/recipes/<slug>.md`. Each recipe is hand-authored, not generated:

- Brief **When to use** statement
- One **L2 demo** (the same component + framework tabs + copy pattern used on component pages)
- Links to each composed component's page
- Optional **Common mistakes** specific to the composition

Recipes ship starting v0.5 (the first phase where overlays make compositions interesting). The recipes sidebar group is auto-discovered from `docs/recipes/*.md`.

## Re-skin gallery

A single marketing page at `teseor.dev/themes` shows the same showcase app (probably `showcase-linear`) rendered with 5–6 themes side-by-side. Ships post-v0.4 once ≥2 themes exist. Proves the theming claim visually in one screen. Built using the same Astro + Teseor stack as the rest of the docs; no extra tooling.
